# RPC 项目测试结果与面试解读

本文汇总项目中已经真实执行的正确性、可靠性、Sanitizer、Release 压测和大文件
E2E 结果。面试时应优先说明测试方法、趋势和工程取舍，不把本机回环数据表述为
生产环境性能。

## 测试环境

- 系统：WSL2，Linux 6.6.87.2，x86_64。
- CPU：Intel Core i5-10505，12 个逻辑 CPU。
- 编译器：GCC 13.3.0，C++17。
- 网络：localhost TCP，但完整经过 Muduo、RPC 编解码和 ZooKeeper 服务发现。
- 存储：WSL 本地文件系统下的临时目录。
- 最新 Release latency 基线：`3188f6847c71a818442b964f6f9ab3f7a5dd235e`。
- 256 MiB/1 GiB E2E 基线：`25c890dc910daee3d10902332b3592e27f2f74da`。

> 注：回环网络消除了真实网络 RTT、丢包和带宽限制，因此这些数据适合验证趋势和
> 定位本机瓶颈，不代表多机生产性能。

## 正确性与可靠性

| 测试 | 结果 | 主要覆盖内容 |
|---|---:|---|
| Debug CTest | 12/12 通过 | Codec、指标、共享 Runtime、业务调度状态、有界执行器、回调容量、文件 Session、过载参数 |
| RPC reliability E2E | 通过 | 异步立即返回、并发乱序响应、超时、取消、断线、Channel 析构、服务端 deadline |
| Provider executor E2E | 通过 | 排队超时、队列拒绝、Reactor 不被阻塞、取消后不进入业务 |
| File transfer E2E | 通过 | 真实上传、手动续传、Provider 重启后自动重试、最终 SHA-256 |
| ASan/UBSan CTest | 12/12 通过 | 测试路径内未发现内存越界、释放后使用和未定义行为 |
| ASan/UBSan RPC E2E | 通过 | RPC 生命周期与异步回调链的动态检查 |
| ASan/UBSan File E2E | 通过 | 上传、恢复、重试和文件发布路径的动态检查 |

### 这组结果能说明什么

- 同步和异步调用共享同一套 request ID、pending、超时、响应分发和一次性完成逻辑。
- 响应、超时、取消和断线发生竞争时，回调只执行一次，最终 active calls 回到 0。
- 多个 `ChannelCore` 可以共享少量 EventLoop；销毁一个 Channel 不影响同 Runtime 下的其他 Channel。
- Provider 的 IO 线程只做拆帧和调度，阻塞业务在线程池执行；队列中的请求先超时后不会再进入业务。
- 文件上传能够在 Provider 中断后根据 sidecar 和 bitmap 恢复，并通过 SHA-256 验证最终内容。

### 这组结果不能说明什么

- ASan/UBSan 不负责发现普通数据竞争；项目尚未把 TSan 作为稳定回归项。
- 单机回环测试不能证明跨机器网络、磁盘故障或长时间运行下的生产稳定性。
- 当前恢复目标是正常进程重启，不承诺突然断电下的 WAL 或数据库事务级一致性。

## 线程模型改造后的 Release Latency

测试日期为 2026-08-27。每组使用 1 MiB 文件、窗口 8、warm connection，每个 uploader
独立预热 3 次；每个并发档统计 100 个成功样本。

| 并发上传数 | 成功/失败 | 吞吐 MiB/s | P50 ms | P95 ms | P99 ms | Client Peak RSS KiB |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 100/0 | 42.97 | 21.00 | 36.02 | 51.11 | 18,556 |
| 4 | 100/0 | 116.42 | 29.80 | 54.98 | 100.00 | 36,548 |
| 8 | 100/0 | 152.26 | 49.60 | 74.12 | 80.04 | 60,528 |

所有档位均为：

- `retry = 0`
- `timeout = 0`
- `network_error = 0`
- `callback_rejected = 0`
- `rpc_active_end = 0`

Provider 在整次 latency profile 中记录到的峰值 RSS 为 59,916 KiB。

### 面试解读

- 并发 8 相比并发 1，吞吐约提升 3.54 倍，但没有线性提升到 8 倍，说明 CPU、文件持久化、
  锁和调度等共享资源逐渐成为限制。
- P99 从 51.11ms 增加到 80.04ms，说明更高并发提升总体吞吐的同时增加了尾延迟。
- `rpc_active_end = 0` 和零回调拒绝说明测试结束后没有遗留 pending call，预留式回调容量
  在该压力下没有成为瓶颈。
- RSS 随并发上升是预期现象，因为同时存在更多上传上下文、Protobuf 消息和分片缓冲区。

> 注：2026-08-24 的旧 latency 数据中并发 8 P99 为 248.74ms；线程模型改造后本次为
> 80.04ms。由于两次本机运行存在环境波动，不能仅凭一次对比宣称改造带来固定比例的
> 性能提升，但可以确认新模型没有引入明显的尾延迟回退。

## 滑动窗口选择

以下是 2026-08-24 的 Release 数据：16 MiB 文件、并发 1、每个窗口 10 次测量。

| 窗口 | 吞吐 MiB/s | 实际最大在途分片 | Client Peak RSS KiB |
|---:|---:|---:|---:|
| 1 | 43.46 | 1 | 17,484 |
| 2 | 44.41 | 2 | 21,032 |
| 4 | 47.57 | 4 | 26,332 |
| 8 | 52.07 | 8 | 34,300 |
| 16 | 49.47 | 14 | 42,072 |

### 面试解读

- 窗口从 1 增加到 8，可以用并发隐藏单个分片 RPC、持久化和响应等待时间。
- 窗口 16 没有继续提升吞吐，内存却继续增长，因此默认窗口选择 8。
- 窗口 8 是当前机器上的实验结果，不是协议常量；真实部署应根据 RTT、带宽、磁盘和
  Provider 容量重新压测。
- 每组只有 10 个样本，因此这组测试只用于选择吞吐窗口，不使用 P95/P99 做稳定结论。

原始数据见 [window CSV](benchmark-release-window-2026-08-24.csv)。该组数据早于最新线程
模型改造，若用于正式性能报告应重新运行；窗口选择的实验方法仍然有效。

## 过载保护

以下是 2026-08-24 的 Release saturation 数据：64 MiB 文件、窗口 8，每档 5 次测量。

| 并发上传数 | 成功 | 失败 | `SERVER_BUSY` | 观察结果 |
|---:|---:|---:|---:|---|
| 1 | 5 | 0 | 0 | 全部完成 |
| 2 | 5 | 0 | 0 | 全部完成 |
| 4 | 5 | 0 | 0 | 全部完成 |
| 8 | 1 | 4 | 4 | 触发有界队列快速拒绝 |

### 面试解读

- 并发 8 时出现 `SERVER_BUSY` 是预期负载保护，不是连接故障。
- 队列满后立即拒绝，避免无限排队引起内存增长和超时雪崩，Reactor 仍可处理轻量请求。
- 5 个样本足以证明拒绝机制被触发，但不足以声称稳定的拒绝率或准确的容量上限。
- 客户端只对超时和连接类瞬态错误重试，不会对明确的 `SERVER_BUSY` 无限重试并放大压力。

原始数据见 [saturation CSV](benchmark-release-saturation-2026-08-24.csv)。该组数据也早于
最新线程模型改造，最终发布前建议重跑以保持实验基线一致。

## 256 MiB 与 1 GiB 大文件 E2E

测试日期为 2026-08-28，使用 Debug 构建、随机文件、1 MiB 分片、窗口 8。测试完整经过
ZooKeeper、Muduo RPC、并行分片上传、服务端临时文件、Finish 发布和两端 SHA-256。

| 文件 | 字节数 | 耗时 | 观察吞吐 | 重试 | 最大在途分片 | 结果 |
|---|---:|---:|---:|---:|---:|---:|
| 256 MiB | 268,435,456 | 2.89s | 88.58 MiB/s | 0 | 8 | PASS |
| 1 GiB | 1,073,741,824 | 43.99s | 23.28 MiB/s | 0 | 8 | PASS |

两组测试中源文件和服务端最终文件的字节数、SHA-256 均完全一致，服务端日志没有
`timeout`、`SERVER_BUSY`、CRC 或文件校验错误。

### 面试解读

- 这组测试首先证明 GiB 级文件能够走完整业务链并正确发布，不是正式 Release 吞吐测试。
- 1 GiB 吞吐明显下降。实现中每确认一个 1 MiB 分片，都会重写 sidecar 并执行一次
  `fsync`；1 GiB 约对应 1024 次元数据同步。这是高可信度瓶颈方向，但尚未使用 `perf`、
  `strace -c` 或 `iostat` 完成定量归因。
- 当前选择优先保证分片确认后的恢复进度。可选优化是按 8～16 个分片或 50～100ms 做
  group commit，并在 Finish 前强制 checkpoint；代价是崩溃恢复时最多重传一个批次。
- 面试中应把它描述为“一致性与吞吐的明确权衡和后续优化方案”，不能宣称当前实现具有
  生产级 GiB 高吞吐。

## 推荐的面试总结

可以用下面这段话概括测试结论：

> 我用单测、真实进程 E2E、ASan/UBSan 和 Release benchmark 分层验证项目。RPC 侧覆盖
> 超时、取消、断线和响应竞争，保证一次完成；文件侧验证乱序分片、重启恢复、过载拒绝
> 和最终 SHA-256。Release 测试中并发从 1 增加到 8，吞吐从 42.97 提升到 152.26 MiB/s，
> 同时 P99 从 51.11 增加到 80.04ms，体现吞吐与尾延迟的权衡。窗口实验选择 8，过载实验
> 能在容量边界返回 SERVER_BUSY。256 MiB 和 1 GiB E2E 都零重试且哈希一致，同时 1 GiB
> 测试暴露了逐分片 fsync 的持久化瓶颈，为后续 group commit 优化提供了依据。

## 数据边界

- 不用本机数据承诺生产 QPS、跨机吞吐或 SLA。
- 不用 5～10 个样本的 window/saturation 数据声称可靠的 P95/P99。
- 不把 `SERVER_BUSY` 统计为网络失败；它是有界系统主动负载 shedding。
- 不把 ASan/UBSan 通过等同于不存在数据竞争。
- 不隐瞒 1 GiB 吞吐下降，重点说明如何定位、如何优化以及优化会改变什么恢复语义。
