# RPC 与大文件上传项目面试问题库

这份文档面向 C++ 后端项目面试。问题按面试官的探究路径组织，而不是按源码文件、
类名或函数名组织。回答时应描述需求、设计、权衡、故障处理和验证结果，不需要背诵
实现名称。

## 使用方法

优先级定义：

- **P0 必会**：简历主动写出的能力，必须能连续回答两到三层追问。
- **P1 高频**：很容易从项目自然延伸出来，至少要能说清原理和项目中的选择。
- **P2 拓展**：用于较深的二面、三面或面试官继续讨论生产化方案。

推荐分六块学习：

| 学习块 | 内容 | 建议顺序 |
|---|---|---:|
| A | 项目叙事、架构和技术选型 | 1 |
| B | 自定义协议、TCP、半包粘包和 Protobuf | 2 |
| C | 同步异步、超时取消、并发状态和 Reactor | 3 |
| D | ZooKeeper、服务发现、路由和连接管理 | 4 |
| E | 大文件分片、幂等、恢复和完整性 | 5 |
| F | 过载保护、压测、工程实践和 C++ 八股 | 6 |

### 回答公式

项目题尽量按以下顺序回答：

1. **场景**：为什么会出现这个问题。
2. **方案**：采用了什么机制。
3. **关键点**：并发、生命周期或数据一致性如何保证。
4. **权衡**：为什么没有选择另一种方案。
5. **验证与边界**：怎样测试，当前不保证什么。

不要只说“用了某个库”或者“加了一把锁”。面试官更关心你是否知道这个机制解决了
什么问题，以及它会引入什么新问题。

### 异常场景总表

面试官往往不会问“你处理了哪些异常”，而是给出一个故障现象，让你沿调用链分析。复习
时先掌握下面这张表，再到对应问题展开细节。

| 场景 | 主要风险 | 项目处理 | 还可生产化改进 |
|---|---|---|---|
| 半包、粘包、非法长度 | 错误拆帧、内存膨胀 | 固定头描述边界，限制最大 body，循环解码 | 连接级速率限制、模糊测试 |
| 协议头或 body 被破坏 | 错误数据进入业务 | 帧 CRC 失败后关闭连接 | TLS/MAC、坏包指标和来源隔离 |
| 响应、超时、取消并发 | 二次回调、状态重复释放 | 统一完成入口和原子状态转换 | 服务端协作式取消 |
| 长连接突然断开 | 在途请求一直等待 | 立即失败该连接上的调用 | 重连退避、熔断、重试预算 |
| 用户回调阻塞或重入 | I/O 线程停顿、死锁 | 投递独立有界执行器，锁外回调 | 专门完成队列、回调耗时监控 |
| 突发流量超过容量 | 无界排队、超时重试风暴 | 有界 outstanding，队满快速拒绝 | 租户配额、令牌桶、熔断和降级 |
| 慢客户端或不完整帧 | 长期占用连接和缓冲区 | 长度上限和调用超时提供基础约束 | 读空闲超时、连接上限和高水位 |
| 分片重复或响应丢失 | 重复写入、状态冲突 | 分片状态、CRC 和磁盘内容共同判定幂等 | 幂等记录过期策略和审计日志 |
| 上传过程中进程重启 | 内存状态丢失 | 临时文件、sidecar 和位图恢复 | WAL/数据库事务和断电一致性 |
| 元数据损坏或孤儿文件 | 错误恢复、磁盘泄漏 | 启动校验并清理非法孤儿 | 隔离区、后台修复和容量告警 |
| ZooKeeper 短暂不可用 | 无法发现新节点 | 已缓存节点短期可用，失败后失效 | watch、熔断和静态兜底地址 |
| 服务节点重启或扩缩容 | 陈旧地址、重复节点 | 临时顺序节点、缓存过期和去重 | 健康权重、优雅摘流和预热 |

# A. 项目叙事、架构和技术选型

## A1. 请你介绍一下这个项目【P0】

**参考回答：**

这是一个基于 C++17、Muduo、Protobuf 和 ZooKeeper 实现的 RPC 框架，并在其上实现了
可恢复的大文件上传服务。RPC 层采用固定长度协议头加 Protobuf 消息体，支持同步与
异步调用、同一长连接上的并发请求、超时、取消、断线处理和服务发现。文件服务支持
乱序并发分片、幂等重试、断点续传、进程重启恢复以及 CRC32 和 SHA-256 完整性校验。

我重点解决了三类问题：第一，TCP 没有消息边界，需要可靠拆帧；第二，异步调用中
响应、超时、取消和断线可能竞争完成同一请求，需要保证只通知一次；第三，大文件传输
不能整文件放入内存，需要分片并发、状态记录和失败恢复。最后通过故障注入 E2E 和
窗口、文件大小、并发数矩阵压测验证完整链路。

**继续追问：** 为什么自己实现 RPC？最难的部分是什么？和成熟框架相比还缺什么？

## A2. 这个项目的整体调用链是什么【P0】

**参考回答：**

客户端先通过 Protobuf 生成的 Stub 发起调用，适配层同步序列化请求，再交给核心调用层
生成请求标识、注册在途状态、选择服务节点并通过长连接发送。服务端从网络缓冲区循环
拆帧，根据服务名和方法名找到业务方法。业务完成后编码响应，客户端通过请求标识找到
原调用，统一处理正常响应、超时、取消或断线。同步调用唤醒等待线程，异步调用投递回调。

文件上传位于 RPC 之上，先初始化会话，再查询缺失位图，用滑动窗口并发上传缺失分片，
全部确认后执行整文件哈希校验并发布最终文件。

## A3. 为什么要分成 Protobuf 适配层、调用核心层和网络层【P0】

**参考回答：**

适配层理解具体的 Protobuf 请求、响应和回调接口；调用核心只管理字节数据、请求状态、
超时、路由和完成通知；网络层负责 EventLoop、连接和缓冲区。这样同步与异步可以复用
同一套传输和响应分发，也能避免核心层被某一种消息类型或裸指针接口绑死。

如果以后增加 Future 或协程接口，只需增加新的上层适配方式，不必重新实现连接、协议、
超时和服务发现。

## A4. 为什么不直接使用 gRPC 或 bRPC【P0】

**参考回答：**

这个项目的目的不是替代成熟框架，而是通过实现关键路径理解 RPC 的协议边界、异步生命
周期、服务发现和故障语义。成熟框架在连接池、流控、安全、可观测性、跨平台、协议兼容
和长期稳定性上明显更完整，生产项目通常优先选成熟框架。

自研的价值是可以针对学习目标控制复杂度，并亲自处理请求关联、半包粘包、超时竞争、
有界队列和文件恢复。回答时不要说“我的框架比成熟框架性能更好”。

## A5. 项目中最难的部分是什么【P0】

**参考回答：**

最难的不是编码，而是异步状态和所有权。一个请求可能同时遇到响应、定时器、取消和连接
断开，任何两条路径都可能并发发生。如果每条路径分别修改状态和执行回调，就可能二次
回调、重复释放或留下悬空指针。

我的处理方式是把每次调用抽象成独立状态，所有结束原因都进入同一个完成入口，通过原子
状态转换和在途表摘除保证只有一条路径获得完成权，并在执行用户代码前释放内部锁。文件
上传则进一步为每个异步分片建立拥有请求、响应和控制对象的上下文。

## A6. 为什么同步和异步要共用一套调用逻辑【P0】

**参考回答：**

两者的网络行为并没有本质区别，都要序列化、生成请求标识、发送、等待响应、处理超时和
断线。区别只在完成后的通知方式：同步调用等待条件变量，异步调用执行回调。如果分别写
两套网络逻辑，很容易出现错误码、超时、重试或协议行为不一致。

共用状态机也便于测试“任何请求只完成一次”这个核心不变量。

## A7. 为什么文件传输作为 RPC 上层业务，而不是塞进 RPC 协议【P0】

**参考回答：**

RPC 协议只应该解决通用的消息边界、路由、请求关联和框架状态；分片大小、文件偏移、
上传会话、位图和文件哈希属于业务语义。把文件逻辑放在上层可以保持 RPC 通用，也能让
文件服务独立演进幂等和恢复策略。

RPC 层仍然限制单帧大小并提供帧校验，文件层则把大文件拆成远小于上限的分片。

## A8. 这个项目目前有哪些明确边界【P0】

**参考回答：**

当前只支持上传，不包含下载、认证、TLS 和跨机房一致性；多个服务实例各自管理本地上传
会话，通过传输标识做粘滞路由，不共享 Session；恢复目标是正常进程重启，不承诺机器
断电后的严格落盘一致性；取消和超时主要终止客户端等待，不会向服务端发送中止执行帧。

这些不是应该掩盖的缺陷，而是为了控制面试项目复杂度而明确划定的范围。

## A9. 你如何证明项目不是“只能跑通 Demo”【P0】

**参考回答：**

验证分三层。单元层覆盖协议篡改、随机分片写入、重复和冲突分片、损坏元数据、空文件和
队列饱和；RPC 可靠性测试覆盖异步立即返回、乱序响应、超时与迟到响应竞争、取消和关闭；
真实 E2E 会启动 ZooKeeper 和多个服务实例，执行普通上传、服务中断、手动恢复、自动重试
和最终哈希对比。

另外做了不同窗口、文件大小和并发上传数的压测，并保存原始结果和测试环境，而不是只写
一个脱离环境的吞吐数字。

## A10. 如果继续生产化，你会优先做什么【P1】

**参考回答：**

第一优先级是安全和可观测性，包括 TLS、认证、请求日志、指标和链路追踪；第二是连接级
与租户级流控，防止单个客户端占满资源；第三是更严格的持久化，例如数据和目录同步、
WAL 或数据库；第四是跨节点共享状态或可迁移的粘滞路由；最后才是无拷贝、内存池等性能
优化。优先级应由故障风险和测量结果决定。

# B. 自定义协议、TCP 和 Protobuf

## B1. 你的协议是怎么设计的【P0】

**参考回答：**

协议使用 28 字节固定头加变长消息体。头部包含协议标识、版本、头长度、消息体长度、
请求标识、消息类型、框架状态码和 CRC32。消息体由元数据长度、Protobuf 元数据和业务
负载组成。请求元数据携带服务名、方法名和超时信息，业务负载是具体请求消息的序列化
结果；响应头携带框架状态，响应元数据携带错误文本，负载是具体响应消息。

固定头用于快速判断边界和合法性，Protobuf 用于结构化内容和接口演进。

## B2. 为什么选择固定长度头部加变长消息体【P0】

**参考回答：**

固定头可以在只收到少量字节时就判断协议、版本和后续长度，拆帧逻辑简单且成本稳定。
变长 body 则避免为不同业务消息预留固定空间。纯分隔符协议不适合任意二进制负载，纯
Protobuf 消息本身也不能直接替 TCP 提供帧边界，所以需要外层长度字段。

## B3. TCP 为什么会有半包和粘包【P0】

**参考回答：**

TCP 提供的是有序可靠字节流，不保留应用层一次写入对应一次读取的边界。一个应用消息
可能被分多次读取，多个消息也可能一次读到。所谓半包和粘包不是 TCP 出错，而是应用层
没有天然消息边界。

解决方式是在协议中携带长度，并在连接缓冲区中循环解析：头部不足就等待；头部完整但
body 不足也等待；完整一帧就消费对应字节并继续解析剩余数据。

## B4. 如何防止恶意长度导致内存问题【P0】

**参考回答：**

读取固定头后先校验协议版本、头长度和 body 上限，再计算完整帧大小。项目将单帧 body
限制为 64 MiB，文件分片默认 1 MiB、最大 4 MiB，不会因为头部声明了一个极大长度就直接
申请对应内存。生产环境还应增加连接级累计缓冲上限、读取超时和每来源限流。

## B5. 为什么不能直接发送 C++ 结构体【P0】

**参考回答：**

C++ 结构体可能包含编译器填充，字段对齐和枚举大小也可能随 ABI 变化，而且不同机器字节
序可能不同。直接发送结构体会把进程内存布局误当成稳定线协议。

项目按固定偏移逐字段写入网络序，接收端也逐字段恢复，因此线协议不依赖结构体大小和
主机端序。

## B6. 为什么协议整数使用大端序，Protobuf body 不转换端序【P0】

**参考回答：**

协议头中的整数由框架自行定义，需要统一网络字节序。Protobuf 已经定义了自己的跨平台
二进制编码，例如 varint 和定长字段编码；序列化后的 body 应视为不透明字节串。如果再
对整个 body 做端序转换，反而会破坏 Protobuf 格式。

## B7. 请求标识解决什么问题【P0】

**参考回答：**

同一条长连接可以同时存在多个在途请求，服务端业务耗时不同，响应顺序不一定等于请求
顺序。客户端通过请求标识把响应映射回对应调用状态，因此不需要按发送顺序阻塞等待。

请求标识只解决“响应属于谁”，不自动提供业务幂等或分布式全局唯一语义。

## B8. 为什么状态码和错误文本要分开【P1】

**参考回答：**

状态码用于程序稳定判断错误类别，例如超时、连接关闭、方法不存在；错误文本用于日志和
人工排查。不能让调用方依赖错误字符串做流程控制。RPC 框架状态与文件业务状态也应分层：
前者表示传输和分发是否成功，后者表示分片、校验或会话状态是否成功。

## B9. CRC32 覆盖哪些内容，为什么校验字段本身要按零处理【P0】

**参考回答：**

帧 CRC 覆盖固定头和 body，但计算时把头中的 CRC 字段视为零。发送端先写零、计算校验值
再回填；接收端采用相同规则。否则校验值会参与自身计算，无法得到一致结果。

CRC32 适合快速发现随机传输错误或测试中的篡改，但不具备密码学抗伪造能力，不能代替
TLS 或消息认证码。

## B10. 收到非法帧为什么直接关闭连接【P1】

**参考回答：**

如果协议标识、长度、消息类型或 CRC 已经非法，继续在当前字节流中猜测边界可能把后续
任意字节误当成新帧，状态不可再信任。项目选择关闭连接，并让该连接上的在途请求统一
得到连接错误。另一种方案是搜索下一个 magic 重新同步，但复杂度和误判风险更高。

## B11. 为什么使用 Protobuf【P0】

**参考回答：**

Protobuf 提供明确 schema、较紧凑的二进制编码、自动生成类型和服务描述信息，适合 RPC
请求响应。框架可以利用服务和方法描述符做通用分发，而不需要为每个业务手写解析代码。

代价是需要管理 schema 兼容和代码生成过程，而且 Protobuf 只解决消息序列化，不解决
TCP 帧边界、超时、连接、服务发现和幂等。

## B12. Protobuf 如何做向前、向后兼容【P1】

**参考回答：**

字段在线上主要由编号识别，新增可选字段通常能被旧端忽略，未知字段也可以被保留。已经
发布的字段编号不能改作其他含义，删除字段后应保留编号，避免未来复用。字段类型变更也要
遵循兼容规则。服务接口升级最好新增字段或新增方法，而不是直接改变旧字段语义。

## B13. 为什么还要在 body 中放元数据长度【P1】

**参考回答：**

外层 body 长度只能确定整帧边界，body 内仍需要区分“通用 RPC 元数据”和“具体业务
负载”。元数据长度让接收方先解析服务、方法、超时或错误信息，剩余字节直接交给目标消息
类型解析，无需扫描分隔符。

## B14. 长连接和短连接怎么选择【P0】

**参考回答：**

RPC 调用频繁且服务地址相对稳定，长连接能减少握手和临时端口开销，也便于多请求复用。
代价是连接生命周期更复杂，一次断线会影响多个在途请求，还需要处理空闲、重连、心跳和
背压。短连接实现简单、故障隔离更直接，但高频调用下连接成本明显。

当前项目按服务节点复用长连接，断线时只完成该节点相关的在途请求。

## B15. TCP 已经可靠，为什么应用层还需要校验和重试【P1】

**参考回答：**

TCP 的可靠性是连接字节流层面的，不代表应用请求一定成功。连接可能在服务端处理完成但
响应返回前断开，磁盘或内存也可能发生数据问题，代码错误还可能构造非法帧。应用层 CRC
用于验证自定义帧，业务重试用于恢复调用，最终文件哈希用于验证业务数据身份。

TCP 重传与 RPC 重试层次不同，不能混为一谈。

# C. 同步异步、并发状态和 Reactor

## C1. 同步调用和异步调用如何实现【P0】

**参考回答：**

两者先走同一套请求注册、定时器、服务发现、连接和发送逻辑。同步调用持有调用状态并在
条件变量上等待完成；异步调用立即返回，完成时把结果写入调用方的响应对象并执行回调。

异步不是“开一个线程执行同步调用”，而是请求发送后不阻塞发起线程，网络响应由
EventLoop 驱动。

## C2. 如何支持一条连接上的多个并发请求【P0】

**参考回答：**

每个请求生成唯一的请求标识，并在发送前注册到在途调用表。收到响应后从协议头取出标识，
找到对应状态并完成。服务端可以并发处理请求并乱序响应，客户端不依赖顺序。

这里的并发是“多个请求同时在途”，不是多个线程同时对同一个 socket 直接写裸字节。

## C3. 为什么必须先注册调用状态再发送【P0】

**参考回答：**

在回环网络或服务很快时，响应可能在发送流程刚结束就到达。如果先发送后注册，响应处理
线程会找不到对应请求并把它当成未知响应。先注册再发送建立了明确的 happens-before
关系，发送失败也通过统一完成入口把状态移除。

## C4. 响应、超时、取消同时发生怎么办【P0】

**参考回答：**

所有结束原因都尝试把调用从 Pending 原子转换到 Completing，并从在途表摘除。只有一个
线程能够成功获得完成权，其他路径发现状态已不存在或转换失败后直接返回。获胜路径写入
结果、取消定时器、标记 Completed，再唤醒同步线程或投递异步回调。

这个机制保证“客户端完成通知至多一次”，不代表服务端业务只执行一次。

## C5. 为什么既要原子状态，又要互斥锁【P0】

**参考回答：**

原子状态只负责竞争一次完成权，适合单个小状态的无锁转换。调用结果、回调、条件变量谓词
和定时器信息是多个字段，需要作为一致整体读写，因此仍由互斥锁保护。原子变量不能自动
让周围所有普通变量线程安全。

## C6. 超时机制是怎么做的【P0】

**参考回答：**

请求发送前后会在网络事件循环中注册一次性定时器，调用状态保存定时器句柄。定时器到期
时提交超时结果，与正常响应竞争同一个完成权。正常响应、取消或断线先完成时会取消定时器。
即使定时器已经进入执行队列，一次完成机制也会阻止二次回调。

## C7. 超时以后服务端还会不会继续执行【P0】

**参考回答：**

可能会。当前超时是客户端停止等待并忽略迟到响应，没有向服务端发送取消帧。如果请求已
到达服务端，业务可能继续执行并产生副作用。因此带副作用操作必须依赖业务幂等键、去重
记录或事务设计，不能把客户端超时理解成“服务端一定没执行”。

## C8. 主动取消如何实现，取消是否可靠【P0】

**参考回答：**

控制对象记录取消状态，并把取消动作关联到具体在途调用。取消与响应、超时一样竞争完成
权，成功后客户端收到取消错误并执行一次回调。当前取消是本地语义，不会强制停止已经在
服务端运行的任务。

生产级远程取消需要单独取消消息、服务端任务注册表和业务对协作式取消的支持，即使如此
也很难保证任意阻塞系统调用立即停止。

## C9. 连接断开时为什么不等待所有请求超时【P0】

**参考回答：**

连接已经确认不可用时，继续等到每个请求自己的 deadline 只会增加无意义延迟并占用状态。
项目记录每个调用所属节点，断线时立即完成该连接上的所有在途请求，并让可重试的上层业务
决定是否重新发送。其他节点上的调用不受影响。

## C10. Channel 销毁时在途请求怎么办【P0】

**参考回答：**

关闭过程先阻止新请求进入，再用明确的关闭错误完成剩余调用，停止连接和定时器，并排空
已经接收的回调任务。不能直接释放网络对象，否则 EventLoop 中排队的任务或用户等待线程
可能访问已销毁状态。

## C11. 异步调用中请求、响应、控制对象和回调谁负责生命周期【P0】

**参考回答：**

Protobuf 原生接口采用借用语义。请求在调用入口同步序列化，调用返回后框架不再访问原请求；
响应、控制对象和回调必须存活到完成回调结束。通用接口无法把调用方的栈对象擅自包装成
拥有型智能指针，否则可能错误 delete 栈内存。

文件上传器在内部为每个异步分片创建共享上下文，由上下文拥有控制对象、请求数据、响应
和重试次数，因此上层用户不接触裸指针生命周期。

## C12. 为什么用户回调不应该直接在 I/O 线程执行【P0】

**参考回答：**

用户回调可能做耗时计算、磁盘访问、加业务锁或再次发起同步 RPC。直接在 I/O 线程执行会
阻塞该线程负责的所有连接，严重时形成死锁。项目正常路径把回调投递到独立执行器，并禁止
在 I/O 线程发起同步 RPC。

当前实现为了不丢完成通知，在回调队列拒绝时存在退化为当前线程执行的兜底。生产化应通过
调用准入、足够容量或专门的完成队列消除这一退化路径。

## C13. 条件变量为什么要使用谓词【P1】

**参考回答：**

条件变量允许虚假唤醒，而且通知可能发生在等待开始之前。等待线程必须在同一互斥锁下检查
“是否已经完成”这个谓词；不满足就继续等待。通知本身不保存业务状态，真正可靠的是受锁
保护的完成标志。

## C14. `notify_one` 和 `notify_all` 如何选择【P1】

**参考回答：**

如果明确只有一个同步线程等待一次调用，`notify_one` 足够；如果状态可能被多个观察者等待，
或无法严格保证等待者数量，可以使用 `notify_all`，所有线程醒来后再检查谓词。选择依据是
等待语义，不是“all 更保险所以永远用 all”。

## C15. 为什么回调执行时不能持有框架内部锁【P0】

**参考回答：**

用户回调属于不可控代码，可能再次调用框架、销毁 Channel、获取其他锁或长时间阻塞。如果
持有在途表或调用状态锁执行，会导致重入死锁、锁顺序反转和全局延迟。正确顺序是先摘除
内部状态并释放锁，再执行回调。

## C16. Reactor 模型是什么【P0】

**参考回答：**

Reactor 使用 I/O 多路复用等待多个文件描述符的就绪事件，事件到达后由事件循环分发给对应
处理器。它通知的是“现在可以读写”，实际读写仍由应用完成，因此通常归类为同步非阻塞 I/O
架构。

Muduo 基于 Reactor，将连接事件归属到固定 EventLoop，减少多个线程同时操作同一连接的
锁竞争。

## C17. Muduo 的 one loop per thread 怎么理解【P0】

**参考回答：**

每个 EventLoop 固定属于一个线程，它管理一组连接和事件回调。其他线程需要修改这些连接
时，不直接并发操作内部状态，而是把任务投递回对应 EventLoop。这样网络状态有清晰的线程
归属，许多数据结构无需到处加锁。

服务端可以有多个 I/O EventLoop 分担连接；客户端项目当前用一个专用 EventLoop 管理不同
服务节点的长连接。

## C18. I/O 线程和业务线程为什么要分开【P0】

**参考回答：**

I/O 线程应该快速完成收包、拆帧、状态分发和发送，避免被磁盘 I/O、哈希计算等慢任务阻塞。
文件服务把磁盘操作投递到有界工作线程池，I/O 线程只完成参数复制和任务提交。这样慢业务
不会阻止其他连接继续收发。

## C19. 如果一个请求处理 10 秒，会发生什么【P0】

**参考回答：**

如果直接在 Reactor 线程处理，该线程上的其他连接会一起停顿；如果交给固定线程池，则会
长时间占用 worker，并可能让后续任务排队。解决方案不只是“增加线程”，还要设置超时、
限制队列、隔离慢任务、快速拒绝，必要时改成异步任务系统。线程数增加过多会带来内存和
上下文切换成本。

## C20. select、poll 和 epoll 有什么区别【P0】

**参考回答：**

select 使用固定大小位图并且每次调用都要重新传递和扫描集合；poll 使用数组，没有同样的
固定 fd 数量限制，但仍需线性扫描；epoll 在内核维护关注集合，等待时返回就绪事件，适合
大量连接中只有少量活跃的场景。不能简单背成“epoll 永远 O(1)”，实际性能还受活跃连接数、
回调工作量和系统调用影响。

## C21. epoll 的 LT 和 ET 有什么区别【P1】

**参考回答：**

水平触发在条件仍满足时会重复通知，编程相对稳健；边缘触发主要在状态发生变化时通知，
通常要求使用非阻塞 fd 并持续读写直到返回 EAGAIN，否则可能长时间收不到下一次通知。ET
不必然更快，错误处理也更复杂，应结合框架实现和测量选择。

## C22. Reactor 和 Proactor 有什么区别【P1】

**参考回答：**

Reactor 通知 I/O 已就绪，应用再执行读写；Proactor 提交异步 I/O 操作，系统在操作完成后
通知应用。Linux 上常见的 epoll 网络框架主要是 Reactor。线程池代替 I/O 线程执行阻塞读写
可以模拟部分 Proactor 流程，但语义和真正内核异步 I/O 不完全相同。

## C23. 为什么不采用一个连接一个线程【P1】

**参考回答：**

连接数较大而大部分时间空闲时，一个连接一个线程会消耗大量栈内存，并产生调度和上下文
切换成本。Reactor 用少量线程等待大量连接，只在事件就绪时执行处理。连接数量很少、业务
逻辑简单时线程模型也可以接受，技术选型应由负载特征决定。

# D. 服务发现、路由和连接管理

## D1. 服务注册和发现是怎么做的【P0】

**参考回答：**

ZooKeeper 中按服务、方法和 Provider 实例组织节点。服务和方法目录是持久节点，具体实例
使用临时顺序节点，节点数据保存地址。客户端查询某个方法下的全部实例，解析并缓存可用
地址，再选择目标建立或复用长连接。

## D2. 为什么使用临时顺序节点【P0】

**参考回答：**

临时节点与会话绑定，Provider 会话过期后 ZooKeeper 自动删除节点，可以表达实例存活性；
顺序后缀为并发注册生成唯一名称，允许同一方法存在多个 Provider，也便于观察注册顺序。

节点删除依赖会话过期，并不是进程断开瞬间完成，因此客户端仍要处理短暂陈旧地址。

## D3. ZooKeeper 如何发现服务下线【P0】

**参考回答：**

Provider 与 ZooKeeper 保持会话和心跳。连接暂时中断时会话未必立即过期；超过协商的会话
超时后，ZooKeeper 删除该会话创建的临时节点。客户端重新读取子节点后不再看到该实例。

当前项目还会在 TCP 连接断开时主动让本地 endpoint 缓存失效，缩短等待服务发现收敛的时间。

## D4. 为什么还需要客户端缓存【P1】

**参考回答：**

如果每次 RPC 都同步查询 ZooKeeper，会把控制面放到请求热路径，增加延迟并放大 ZooKeeper
压力。项目维护数秒的短期缓存，平衡查询成本与地址新鲜度；ZK 会话丢失或 TCP 断线时主动
失效相关缓存。

代价是存在短暂陈旧窗口，所以连接失败必须作为正常路径处理，不能假设发现结果永远有效。

## D5. 为什么没有直接依赖 ZooKeeper watch 实时更新【P1】

**参考回答：**

ZooKeeper watch 是一次性通知，触发后需要重新注册；断线期间也可能收不到普通 watch，仍需
处理会话状态和重新读取。第一版采用短 TTL 加故障失效，逻辑更简单且足以满足项目规模。

生产化可以加入子节点 watch，但仍应把 watch 当作“提醒重新读取”，不能把它当成完整事件
日志。

## D6. 如何做负载均衡【P0】

**参考回答：**

无状态普通 RPC 在可用节点间轮询，避免长期固定落在一个实例。有状态文件上传根据传输标识
做稳定哈希，让同一会话的初始化、分片、查询和完成请求落到同一个 Provider。

当前不是完整一致性哈希，节点列表变化可能改变映射；它适合本地 Session 的面试项目，生产
环境可使用一致性哈希、共享状态存储或由服务端返回明确的会话节点信息。

## D7. 为什么文件上传不能简单轮询【P0】

**参考回答：**

每个 Provider 只管理自己的本地临时文件和会话位图。如果同一文件的不同分片被轮询到不同
节点，后续节点找不到会话，甚至形成多份不完整文件。因此有状态调用必须粘滞到同一节点，
或者把会话状态和文件存储放到所有节点共享的系统中。

## D8. Provider 快速重启会有什么问题【P1】

**参考回答：**

旧进程异常退出后，旧临时节点可能要等会话超时才删除；新进程又会注册新节点，因此短时间
内可能出现两个节点指向同一地址。客户端读取后按地址去重，避免轮询权重和稳定哈希被重复
节点扰动。即使拿到陈旧地址，连接失败也必须能够快速返回或重试。

## D9. ZooKeeper 不可用时已有 RPC 能否继续【P1】

**参考回答：**

取决于是否已有有效地址缓存和连接。已有长连接理论上可以继续承载数据面请求，新的服务
发现和地址变更则会受影响。当前实现比较保守，发现会话失联后会清理缓存；生产系统可以在
可用性和陈旧风险之间设计 stale-while-revalidate 策略。

## D10. 一条连接对应什么粒度【P1】

**参考回答：**

当前按服务节点地址维护一条可复用连接，同一节点上的不同方法共享。这样连接数量可控，
也能在断线时按节点完成相关请求。生产环境可能为每个 endpoint 维护连接池，以减少单连接
队头阻塞和提高吞吐，但同时会增加连接管理和请求调度复杂度。

## D11. 长连接断开后如何重连【P1】

**参考回答：**

断线先完成该连接上的在途请求并淘汰失效会话；后续重试或新请求重新选择节点、创建客户端
连接，并在连接建立前暂存待发送帧。要避免多个请求同时发现未连接而重复发起连接，因此
连接会话需要明确的 connecting 状态或统一由 EventLoop 串行管理。

## D12. 服务发现和负载均衡还有哪些生产级改进【P2】

**参考回答：**

可以增加健康检查、权重、最少请求数、延迟感知、熔断、异常节点退避、跨机房优先级和配置
版本；客户端还要限制同时连接数并记录选择结果。选择算法必须结合业务是否有状态、请求
成本是否均匀以及节点扩缩容频率，而不是只比较算法名字。

# E. 大文件上传、幂等、恢复和完整性

## E1. 设计一个高并发大文件上传服务，你会怎么做【P0】

**参考回答：**

先把流程拆成初始化、分片上传、状态查询、完成提交和主动终止。初始化协商分片大小并返回
传输标识；客户端按偏移并发上传分片；服务端用位图记录已接收分片并支持查询；全部分片
完成后校验整文件哈希并原子发布。失败时客户端使用同一传输标识查询缺失位图，只补缺块。

并发方面使用随机偏移写入，分片状态在锁内预占、磁盘 I/O 在锁外执行；资源方面限制分片
大小、窗口、任务队列和会话空闲时间。

## E2. 为什么不直接一次 RPC 发送整个文件【P0】

**参考回答：**

整文件会造成巨大内存峰值、长时间占用单次调用、失败后只能从头重传，也更容易超过消息
大小限制。分片可以限制单次内存、并发利用带宽、单块重试和断点续传。代价是需要会话、
位图、幂等和最终合并校验。

## E3. 分片大小如何选择【P0】

**参考回答：**

分片太小会增加 RPC 次数、协议开销、元数据更新和磁盘系统调用；太大会增加单块内存、
超时重试成本和尾延迟。项目默认 1 MiB、最大 4 MiB，是面向本机测试的折中，并允许客户端
提出偏好后由服务端限制。

生产环境应根据网络带宽时延积、磁盘吞吐、并发数和失败率压测，而不是把 1 MiB 当成通用
最优值。

## E4. 如何支持乱序并发分片【P0】

**参考回答：**

每个分片携带传输标识和绝对偏移，服务端校验偏移必须位于分片边界，并根据文件总大小计算
该位置的准确长度。写入使用显式偏移的随机写接口，不依赖共享文件游标，因此不同分片可以
并行写到固定位置。位图而不是“最大偏移”用来判断完整性。

## E5. 为什么使用随机写接口而不是文件流 seek 后 write【P0】

**参考回答：**

普通文件流维护共享当前位置，多个线程 seek 和 write 容易互相覆盖，需要把整个操作串行化。
随机写接口把 offset 作为每次系统调用参数，不修改共享文件偏移，更适合不同分片并发。仍然
要循环处理信号中断和部分写入。

## E6. 分片状态为什么需要 Missing、Writing、Received 三种【P0】

**参考回答：**

只有缺失和已完成无法表示“某个线程正在锁外写磁盘”。两个重复请求可能同时看到缺失并
写同一位置。增加 Writing 后，第一个线程在锁内预占，其他同分片请求快速返回忙；不同分片
仍可并行。写入或元数据提交失败时再回滚为 Missing。

## E7. 为什么 bitmap 比 next offset 更合适【P0】

**参考回答：**

乱序上传时不存在唯一的“下一个偏移”。即使最高偏移很大，中间仍可能缺块。bitmap 用一个
bit 表示一个分片是否确认，既能准确判断完整性，也便于客户端查询和压缩传输。已接收字节数
用于进度展示，不能单独证明没有空洞。

## E8. 如何处理最后一个分片和空文件【P1】

**参考回答：**

普通分片长度等于协商大小，最后一块长度是“文件剩余字节数”，服务端根据偏移重新计算，
不完全相信客户端。空文件的分片数为零，不接受分片上传，但可以直接进入最终 SHA-256 校验，
空文件也有确定哈希值。

## E9. 重复分片如何做到幂等【P0】

**参考回答：**

如果位图显示分片已完成，先比较持久化的分片 CRC；不同则返回冲突，相同再读取对应磁盘
内容进行字节比较。完全一致时返回成功并标记为重复请求，不重复增加已接收字节数。

仅比较 CRC 不够严格，因为 CRC32 存在碰撞；直接盲目覆盖又可能掩盖客户端逻辑错误。

## E10. RPC 重试为什么必须考虑幂等【P0】

**参考回答：**

连接断开或超时时，客户端无法判断服务端是没收到、执行中，还是已经执行但响应丢失。重试
可能让同一操作执行两次。文件分片通过传输标识和偏移形成业务幂等键，服务端识别相同内容
的重复提交；普通有副作用 RPC 也需要业务请求号、去重表或事务约束。

不要声称 RPC 框架天然提供 exactly-once，它通常最多提供 at-most-once 通知或 at-least-once
尝试，业务执行语义要单独设计。

## E11. 断点续传如何实现【P0】

**参考回答：**

客户端保留传输标识，重新连接后先用相同文件信息恢复会话，再查询服务端的文件大小、分片
大小和接收位图。客户端校验这些信息与本地文件一致，只把缺失分片重新放入调度队列，全部
成功后再完成提交。

传输标识必须路由回保存该会话的 Provider，或者会话状态需要共享存储。

## E12. 服务重启后如何恢复会话【P0】

**参考回答：**

每个会话有临时数据文件和 Protobuf sidecar。sidecar 保存文件信息、分片位图和每块 CRC。
分片写入成功后，通过“写临时元数据、同步、rename”原子替换 sidecar。服务启动扫描合法的
元数据与数据文件，重建内存状态和已接收字节数，损坏或无配对元数据的孤儿文件被清理。

## E13. 为什么先写临时文件，完成后再 rename【P0】

**参考回答：**

上传过程中数据不完整，不能让读取者把它当成最终文件。临时路径只对上传会话可见，所有
分片和 SHA-256 校验成功后再 rename 到完成目录。同一文件系统中的 rename 能提供原子名称
替换语义，读取者看到的是未发布或完整发布状态。

## E14. `ftruncate` 是不是提前分配了所有磁盘空间【P1】

**参考回答：**

不是。它设置文件的逻辑大小，文件系统可能创建稀疏文件，并不保证所有数据块已经分配。
它的主要价值是固定随机写边界。若要更早暴露磁盘空间不足，可以考虑 `posix_fallocate`，
但也要评估其延迟和文件系统支持。

## E15. 为什么需要三层完整性校验【P0】

**参考回答：**

RPC 帧 CRC32 校验一次传输帧的头和 body；分片 CRC32 在写盘前验证具体块，并辅助重复请求
快速判断；完整文件 SHA-256 在提交时确认最终文件身份。三者作用范围和成本不同，不能简单
互相替代。

CRC32 不是安全认证，恶意攻击场景仍需要 TLS、MAC 或签名。

## E16. 为什么最终哈希使用流式计算【P1】

**参考回答：**

大文件不能整体读入内存。流式哈希以固定缓冲区循环读取，依次更新摘要上下文，内存占用与
文件大小无关。项目使用 OpenSSL 高层 EVP 接口，便于管理算法上下文和检查每一步错误。

## E17. sidecar 的 rename 原子是否等于断电安全【P0】

**参考回答：**

不等于。rename 保证命名空间切换的原子可见性，但要严格保证断电后数据和目录项落盘，还
需要考虑数据文件同步、元数据文件同步、目录 fsync 和文件系统语义。当前项目只承诺正常
进程重启恢复，明确不承诺断电级事务一致性。

## E18. 进程在哪些时刻崩溃会发生什么【P1】

**参考回答：**

分片写入前崩溃，位图仍是缺失，客户端重传；数据写完但 sidecar 未提交时崩溃，恢复后仍
视为缺失并安全覆盖；sidecar 已提交但响应未返回时崩溃，客户端重试会走重复分片幂等检查；
最终 rename 后但客户端没收到响应，当前完成会话已移除，生产化还应保存一段时间的完成
记录，使 Finish 本身也幂等。

最后一种是当前实现值得继续改进的边界。

## E19. 如何清理长期未完成的上传【P1】

**参考回答：**

会话记录最近活动时间，后台线程周期扫描超过空闲阈值且没有分片正在写入的会话，将其标记
过期、关闭文件并删除临时文件和 sidecar。清理不能与分片写入或最终提交并发破坏状态，因此
要遵守统一的状态机和锁顺序。

## E20. 如何避免路径穿越【P1】

**参考回答：**

服务端不直接接受任意保存路径，只接受单个文件名，并拒绝绝对路径、父目录、斜杠、反斜杠
和内嵌 NUL。最终路径由服务端受控目录和传输标识拼接。生产环境还要考虑符号链接、目录 fd
相对操作、权限和配额，不能只依赖字符串替换。

# F. 过载、压测、工程实践与 C++ 延伸

## F1. 突然有大量请求涌入，系统会发生什么【P0】

**参考回答：**

如果无限接收并排队，内存、文件描述符和等待延迟会持续增长，超时后客户端重试又会放大
流量，最终形成级联故障。项目把文件磁盘任务放入有界执行器，限制“执行中加排队中”的
outstanding 数量，队列满时立即返回服务繁忙，不阻塞 I/O 线程。

这属于 load shedding。生产化还需要连接级限流、每用户配额、重试预算、熔断和监控。

## F2. 为什么队列满时拒绝比阻塞提交更好【P0】

**参考回答：**

如果 I/O 线程阻塞等待队列空间，它将无法继续读取其他连接、发送已有响应或处理轻量请求，
局部过载会扩散成整个服务不可用。快速拒绝让客户端明确获得可重试错误，同时保持服务处理
已接受任务和恢复健康的能力。

## F3. 有界队列的容量怎么设置【P0】

**参考回答：**

当前默认 4 个 worker、最多 32 个 outstanding，是面试项目的可配置基线，不是普适最优值。
真实设置要根据任务平均与尾部耗时、内存占用、磁盘并发能力、可接受排队时间和到达率测量。

可以用近似排队时间判断：队列越长，等待时间越容易超过调用 deadline，已经注定超时的任务
继续排队没有价值。

## F4. 工作线程数是不是越多越好【P0】

**参考回答：**

CPU 密集任务通常接近核心数，阻塞 I/O 任务可以适当更多，但最终受磁盘队列深度、内存、
锁竞争和上下文切换约束。文件写入和哈希混合了 I/O 与 CPU，应该通过压测观察吞吐和尾延迟。
线程过多可能让随机写更差，并增加每线程栈内存。

## F5. 客户端为什么使用滑动窗口【P0】

**参考回答：**

完全串行不能充分利用网络和服务端并发能力，一次性发送全部分片又会占用大量内存和在途
状态。滑动窗口限制最多 N 个异步分片在途，每完成一个再补一个，在吞吐与资源上限之间取得
平衡，也是一种应用层背压。

## F6. 窗口越大吞吐一定越高吗【P0】

**参考回答：**

不一定。窗口从 1 增大时通常能隐藏网络和磁盘等待，但超过服务端 worker、磁盘并发或连接
容量后，收益会饱和，甚至因排队、锁竞争、缓存压力和重试增加而下降。项目压测中不同窗口
并非严格单调，也说明必须以测量结果选择。

## F7. 哪些错误应该重试【P0】

**参考回答：**

项目只重试超时、网络错误和连接关闭等可能瞬时恢复的传输错误。参数非法、CRC 错误、会话
冲突和业务状态错误通常是确定性问题，原样重试没有意义。重试还必须满足剩余 deadline、
次数预算和业务幂等三个条件。

当前自动重试主要覆盖分片数据面；初始化、查询和最终提交还可以进一步设计独立重试和幂等。

## F8. 为什么使用指数退避，是否还缺什么【P0】

**参考回答：**

连续立即重试会在故障时制造重试风暴。项目采用 100、200、400ms 指数退避，为服务恢复留出
时间。生产环境还应加入随机抖动，避免大量客户端在相同时间点同步重试，并设置全局重试预算
和最大 deadline。

## F9. RPC 超时应该怎么设置【P1】

**参考回答：**

超时应根据端到端延迟分布和业务 SLA 设置，既包括排队、连接、发送、服务处理和回包，不能
只等于服务端平均执行时间。过短会制造无效取消和重试，过长会占用资源并放大故障。更合理的
模型是绝对 deadline 向下游传播，各阶段使用剩余预算。

## F10. 超时、重试和过载为什么容易形成级联故障【P0】

**参考回答：**

服务变慢后请求开始超时，客户端重试使到达率进一步升高；无界队列又增加等待时间，让更多
请求超时，最终形成正反馈。防护需要组合使用短队列、快速拒绝、退避与抖动、重试预算、
deadline、熔断和降级，而不是单独增加机器或线程。

## F11. 如何保证某个客户端不会占满所有资源【P2】

**参考回答：**

当前只有全局 outstanding 和客户端窗口，没有租户公平性。生产化可以增加每连接、每用户、
每传输的并发和字节配额，采用加权公平队列或令牌桶，并把控制请求与大分片任务分池隔离。
还要限制未完成 Session 数和临时磁盘总量。

## F12. 你是怎么压测的【P0】

**参考回答：**

压测固定测试环境，组合不同文件大小、滑动窗口和并发上传数，每组重复运行，记录成功数、
总耗时、吞吐以及 P50、P95、P99 延迟。文件服务在真实 ZooKeeper 和 RPC 链路上运行，最终
结果还要做哈希校验，避免只测到“请求返回”却没有验证数据正确。

## F13. 为什么不能只看 QPS 或吞吐【P0】

**参考回答：**

吞吐高可能以巨大队列和尾延迟为代价，也可能伴随错误率上升。至少要同时看成功率、吞吐、
并发数、P50/P95/P99、CPU、内存、网络、磁盘 IOPS 和队列长度。对文件业务还要区分 RPC 数
和有效字节吞吐。

## F14. P50、P95、P99 分别表示什么【P0】

**参考回答：**

P50 描述典型请求，P95/P99 观察慢请求和尾延迟。例如 P99 为 100ms，表示约 99% 样本不超过
100ms。高分位对样本数量很敏感，只有几个样本时 P99 几乎没有统计意义，因此项目结果明确
标注重复次数少、环境为 WSL2 回环 Debug 构建，只用于趋势观察。

## F15. 当前压测结果说明了什么【P0】

**参考回答：**

本机结果中所有 48 次上传成功。8 MiB、单上传时窗口从 1 到 8，吞吐从约 12.7 MiB/s 提升到
约 17.3 MiB/s；窗口 8、并发 2 时约 21.9 MiB/s。这说明并发能隐藏部分等待，但不同窗口并非
严格单调，瓶颈还包含每块 sidecar 同步、磁盘、连接建立和 Debug 开销。

不能把本机回环结果宣传成生产性能。

## F16. 如何定位性能瓶颈【P1】

**参考回答：**

先用分层指标判断 CPU、网络、磁盘、队列还是锁，再用 profiler 和系统工具验证。CPU 可看
热点和上下文切换，磁盘看吞吐、延迟和队列深度，网络看带宽、重传和连接状态，应用看各阶段
耗时、在途数和拒绝数。一次只改变一个参数，建立基线后再优化。

## F17. 你做了哪些故障注入【P0】

**参考回答：**

包括修改协议头和 body 验证 CRC、服务端延迟制造超时和迟到响应、并发乱序返回、主动取消、
队列饱和、分片 CRC 错误、重复和冲突分片、损坏 sidecar、传输中杀死 Provider、重启后手动
续传，以及客户端自动重试后完成哈希对比。

## F18. 为什么测试要让响应乱序【P0】

**参考回答：**

顺序响应无法证明请求标识和在途表真正生效，错误实现也可能侥幸通过。让服务端按不同延迟
倒序完成，可以验证同一长连接上的多个请求能够根据请求标识找到各自响应，而不是错误地按
发送顺序匹配。

## F19. 如何测试超时只回调一次【P0】

**参考回答：**

让服务端处理时间大于客户端超时，先等待超时回调，再继续等待迟到响应到达，最后检查回调
计数仍为一且错误类型为超时。同理可以让取消、断线和关闭与响应竞争，验证统一完成状态机。

## F20. 测试通过是否意味着线程安全【P1】

**参考回答：**

不意味着。并发 bug 依赖时序，普通测试只能覆盖部分执行。还应使用压力循环、故障注入、
ThreadSanitizer、AddressSanitizer、锁顺序审查和明确线程归属。项目运行过 ASan/UBSan 核心
回归，但还可以增加 TSan 专项测试和更长时间稳定性测试。

## F21. RAII 在项目中有哪些应用【P0】

**参考回答：**

文件描述符使用独占资源对象，析构自动 close；OpenSSL 摘要上下文由带自定义删除器的智能
指针管理；调用状态和异步上下文通过共享所有权跨线程存活；互斥锁使用作用域锁对象。RAII
把释放动作绑定到对象生命周期，减少错误分支遗漏清理。

## F22. `unique_ptr`、`shared_ptr` 和 `weak_ptr` 如何选择【P0】

**参考回答：**

独占资源优先 `unique_ptr`，例如某个连接会话独占网络客户端；确实需要多个异步参与者共同
延长生命周期时使用 `shared_ptr`；回调需要观察对象但不应阻止销毁时使用 `weak_ptr` 打破
循环。智能指针表达所有权，不应该为了“看起来安全”把所有裸指针都改成 `shared_ptr`。

## F23. 为什么 Protobuf 接口里的裸指针不能直接交给 shared_ptr【P0】

**参考回答：**

裸指针只是借用，不表示所有权转移。调用方可能传入栈对象，若框架直接构造默认删除器的
`shared_ptr`，引用计数归零时会对栈内存执行 delete。即使使用空删除器，也没有延长对象真实
生命周期，只是把悬空风险藏起来。

## F24. 原子 compare-exchange 在这里解决什么【P0】

**参考回答：**

它比较当前状态是否仍为 Pending，只有相等时原子改成 Completing；失败时还会把实际值写回
expected。这样多个完成来源并发时只有一个成功。strong 不允许无原因的伪失败，适合这里
只尝试一次的状态转换；weak 更适合放在循环中重试。

## F25. memory order 怎么理解【P1】

**参考回答：**

原子性解决操作不可分割，内存序解决普通内存访问在不同线程之间的可见顺序。默认
`seq_cst` 为相关原子操作提供最强的全局顺序，但不等于所有线程串行执行，也不能修复普通
变量的数据竞争。项目在发布完成状态时使用 release、读取时使用 acquire，复杂复合状态仍
由 mutex 保护。

## F26. mutex 和 atomic 的使用边界是什么【P0】

**参考回答：**

单个计数或简单状态转换可以用 atomic；多个字段需要保持一致、需要条件变量或临界区包含
容器操作时使用 mutex。无锁不一定更快，错误的内存序也更难维护。项目只用原子争夺完成权
和统计计数，结果对象、回调和映射仍使用锁。

## F27. 为什么任务 lambda 有时需要 mutable【P1】

**参考回答：**

按值捕获的成员默认在 lambda 的 `operator()` 中视为 const。如果要把捕获的字符串或智能
指针继续 move 给下一层，需要 `mutable` 允许修改捕获副本，否则 `std::move` 可能得到 const
右值，最终无法调用移动构造而退化为复制。

## F28. 移动语义在项目中有什么价值【P1】

**参考回答：**

请求帧、分片数据和响应 payload 可能较大，跨任务队列和完成回调时使用移动语义可以转移
内部缓冲区，避免重复复制。标准容器和字符串已经实现移动构造、移动赋值，因此业务结果
结构通常无需手写移动函数；手写反而可能抑制编译器自动生成。

## F29. 为什么文件描述符要用 RAII 类，而不是保存 int【P1】

**参考回答：**

裸 int 无法表达所有权，错误返回、异常或容器销毁时容易忘记 close，也可能发生重复关闭。
RAII 对象禁止复制、允许移动，确保任意时刻只有一个所有者，离开作用域自动释放。

## F30. unordered_map 为什么适合保存并发调用状态【P1】

**参考回答：**

响应通过请求标识做精确查找，哈希表平均 O(1)，不需要有序遍历。它仍需要考虑 rehash、内存
占用和并发保护。当前用互斥锁保护注册与摘除；更高性能框架可能按 EventLoop 分片、使用
槽位 ID 或无锁结构，避免全局哈希锁。

## F31. 工程上如何设计错误码【P1】

**参考回答：**

错误应按层次划分：协议解析、序列化、服务分发、网络传输、调用生命周期和文件业务。程序
使用稳定错误码，日志使用上下文文本；要区分可重试与不可重试，并保证新增错误不会改变旧
错误语义。不能把所有断线、超时和业务失败都叫 network error。

## F32. 如何做优雅关闭【P1】

**参考回答：**

先停止接收新请求，标记组件关闭；完成或取消在途调用；停止定时器和连接；工作线程池根据
策略排空已接收任务；最后 join 线程并释放资源。关闭过程中不能持有内部锁执行用户回调，
也要避免从 worker 线程 join 自己。

## F33. 应该记录哪些日志和指标【P1】

**参考回答：**

日志需要请求标识、服务方法、节点、错误码、耗时、重试次数和传输标识，但不能记录敏感
文件内容。指标至少包括请求率、成功率、各错误类型、延迟分位数、在途请求、连接数、队列
长度、拒绝数、分片吞吐、重试和 Session 数。生产系统还应加入 trace，把一次调用跨层关联。

## F34. 如何做配置管理【P2】

**参考回答：**

地址、超时、线程数、队列容量、分片大小和存储目录不应散落硬编码；需要默认值、范围校验、
启动时打印生效配置和敏感信息隔离。动态配置还需要版本、原子切换和回滚。当前项目采用配置
文件和调用级选项，尚未实现动态配置中心。

## F35. 如何上线和回滚协议升级【P2】

**参考回答：**

头部携带版本，解码端先校验支持范围。兼容升级应保证新旧节点能同时存在，Protobuf 字段只
新增不复用，必要时按版本选择编码器。发布采用灰度，监控解析错误和旧版本流量；出现异常
时能回滚服务，同时保留旧协议读取能力。

## F36. 项目出现线上故障你会怎么排查【P0】

**参考回答：**

先确认影响范围和时间线，再按客户端、服务发现、连接、队列、业务线程池和磁盘分层看指标。
大量超时要区分连接失败、排队过长、磁盘慢和回调线程阻塞；数据错误要根据传输标识核对
分片位图、CRC、sidecar 和最终哈希。先止损，例如限流、关闭重试或摘除异常节点，再保留
日志、core、配置和压测复现条件定位根因。

## F37. 为什么 CMake 和依赖管理也可能被问【P1】

**参考回答：**

工程能否重复构建也是项目质量的一部分。需要知道头文件搜索路径、静态库与动态库、链接
顺序、`-lprotobuf` 等链接参数，以及代码生成如何成为构建依赖。项目使用 CMake 查找
Protobuf、OpenSSL 和 zlib，并在构建期从 proto 生成 C++ 源码，再链接到对应目标。

## F38. 如何评价当前项目质量【P0】

**参考回答：**

它已经完整覆盖 RPC 和可恢复上传的核心链路，有明确错误语义、并发状态机、故障测试和真实
压测，不只是 happy path。但它仍是单机存储、面试规模实现，缺少安全、可观测性、严格落盘
和跨节点状态。合理的评价应该同时给出已验证能力和未解决边界，而不是把它包装成生产框架。

## F39. 慢客户端会带来什么问题【P1】

**参考回答：**

客户端长时间只发送一部分协议头或 body，会持续占用连接、解码缓冲区和服务端状态；客户端
长期不读响应，又会让发送缓冲区增长并拖慢连接。长度限制只能限制单帧大小，不能解决时间
维度上的资源占用。生产环境还需要读写空闲超时、连接数上限、单连接缓冲高水位和来源限速。

## F40. 服务端发送速度大于客户端接收速度时怎么办【P1】

**参考回答：**

非阻塞发送并不保证数据立即进入网络，未发送部分会留在用户态或内核发送缓冲区。如果业务
持续生产响应，内存可能不断增长。应监控输出缓冲高水位，暂停继续生产或读取、限制每连接
在途响应，必要时关闭长期不消费的连接。这是网络层背压，与业务线程池的有界队列共同构成
端到端流量控制。

## F41. 文件描述符耗尽时系统会怎样，如何防护【P1】

**参考回答：**

连接和打开的临时文件都会消耗文件描述符。达到进程限制后，新连接、打开文件甚至部分日志
操作都可能失败。防护包括限制连接和上传会话数、及时关闭资源、监控使用量、合理设置系统
上限，并为接收连接失败预留处理策略。只提高系统上限而不控制资源增长，会把故障推迟而非
解决。

## F42. 超时为什么应使用单调时钟【P1】

**参考回答：**

超时表示持续时间，应该使用不会因系统校时而跳变的单调时钟。墙上时钟可能被 NTP 或人工
调整，导致定时器提前或延后。日志时间使用系统时钟便于和现实时间对应，deadline 和耗时
计算使用单调时钟，两者用途不同。

## F43. 如何降低死锁风险【P0】

**参考回答：**

先明确每份状态的线程归属，尽量让连接状态只在所属事件循环修改；必须使用多把锁时规定
固定加锁顺序，并缩短临界区。不要持锁执行用户回调、阻塞 I/O 或等待另一个线程完成，也
不要在工作线程中等待自己所属线程池的任务。排查时结合线程栈、锁等待和最小复现，而不是
靠增加超时掩盖死锁。

## F44. 用户回调抛出异常怎么办【P1】

**参考回答：**

异常如果逃出线程入口，可能触发进程终止；逃出公共框架边界也会破坏完成线程。当前执行器
在任务边界捕获所有异常，保证工作线程继续服务，但尚未记录异常详情。生产化应记录请求
上下文和异常原因，并维护失败统计。框架不能猜测业务如何恢复，因此不应静默重试整个有
副作用操作。

## F45. 什么是惊群，和这个项目有什么关系【P2】

**参考回答：**

惊群是一个事件或恢复信号同时唤醒大量等待者，最终只有少数获得资源，其余线程产生无效
竞争。网络 accept、条件变量广播以及大量客户端在同一时刻重试都可能出现类似现象。项目
按等待者数量选择单个或全部通知，并通过指数退避降低同步重试；生产环境还应加入随机抖动，
让恢复流量在时间上摊开。

# 面试中的高风险表述

以下说法容易被继续追问后推翻，应主动避免：

| 不严谨说法 | 更准确的表达 |
|---|---|
| TCP 有粘包 bug | TCP 是字节流，应用层需要自行定义消息边界 |
| 超时后请求没有执行 | 客户端停止等待，服务端可能没执行、执行中或已完成 |
| CAS 保证 exactly-once | CAS 只保证客户端完成通知至多一次 |
| CRC32 能保证安全 | CRC32 检测随机错误，不提供抗恶意篡改能力 |
| rename 保证断电一致性 | rename 保证原子可见性，严格落盘还需 fsync 等机制 |
| ftruncate 提前占满磁盘 | 它设置逻辑大小，文件可能是稀疏的 |
| epoll 所有操作都是 O(1) | 它避免每次传全量关注集合，成本仍与就绪事件和回调有关 |
| 线程越多吞吐越高 | 线程受 CPU、I/O、锁和切换成本约束，需要压测 |
| Protobuf 解决了 RPC | Protobuf 解决 schema 和序列化，RPC 还需传输与调用语义 |
| shared_ptr 能解决悬空指针 | 只有获得真实所有权才能延长生命周期 |
| 使用 ZooKeeper 就是强一致服务发现 | 临时节点和缓存仍存在会话超时与陈旧窗口 |
| 窗口越大上传越快 | 超过系统容量后收益饱和，甚至加重排队和尾延迟 |
| 测了本机吞吐就是生产性能 | 必须说明环境、构建类型、样本数和瓶颈 |
